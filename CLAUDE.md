# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Explorify is a Next.js + TypeScript web app that gives Spotify users endless music and artist recommendations based on the song they're currently listening to, helping them explore music outside their usual taste profile. It was migrated from a client-only Create React App to Next.js specifically to fix an insecure implicit-grant OAuth flow (token only in React state, lost on every refresh) and to move all Spotify API access server-side; it was later converted from JavaScript to TypeScript for compile-time safety around the Spotify Web API response shapes.

## Commands

- `npm install` — install dependencies (also regenerates `package-lock.json`, which was reset by the CRA→Next.js migration). `--legacy-peer-deps` is no longer required: Material-UI v4 was the source of the React 18 peer conflict and has been removed.
- `npm run dev` — dev server (http://127.0.0.1:3000 — Spotify requires `127.0.0.1`, not `localhost`, for local redirect URIs)
- `npm run build` — production build (also runs Next's TypeScript + ESLint checks)
- `npm start` — run a production build
- `npm run lint` — `next lint` (`next/core-web-vitals`)
- `npx tsc --noEmit` — type-check only, faster feedback loop than a full build

Requires `.env.local` (see `.env.local.example`): `SPOTIFY_CLIENT_ID`, `SPOTIFY_CLIENT_SECRET`, `NEXTAUTH_SECRET`, `NEXTAUTH_URL`. No test suite exists.

## Architecture

**Auth (the core fix):** `src/lib/auth.ts` configures next-auth (Auth.js v4) with the Spotify provider and `session: { strategy: "jwt" }` — no database. The `jwt` callback stores `accessToken`/`refreshToken`/`accessTokenExpires` on sign-in and silently refreshes the access token server-side (via Spotify's `/api/token` refresh grant) whenever it's expired, before any Spotify call uses it — this is what lets a session survive a page refresh instead of forcing re-login every time. **Security boundary:** the `session` callback deliberately never copies `accessToken`/`refreshToken` onto the `session` object. It is **not** an allowlist — next-auth hands it a session already populated with `user.name`/`user.email`/`user.image` (off the JWT) plus `expires` (`node_modules/next-auth/core/routes/session.js:61-72`), and our callback (`auth.ts:87-95`) only *adds* `user.id` and `error`. So assume everything sitting on `session` is servable to the browser via `useSession()` / `GET /api/auth/session`; the security property is what is never added, not some short list of what is. (`user.email` is empty in practice — `authorization` in `auth.ts` replaces next-auth's default Spotify scope string, whose only scope is `user-read-email`, and `SPOTIFY_SCOPES` doesn't re-request it — but don't design around that. **Trap:** the code comment at `auth.ts:88` still describes the callback as an allowlist; it is wrong.) Route handlers instead call `getAccessToken(req)` / `getSpotifySession(req)` from `src/lib/spotifyApi.ts`, which use `getToken()` from `next-auth/jwt` to decrypt the httpOnly session cookie directly, server-side only — the raw Spotify token never reaches client JS. The `Session`/`JWT` field shapes above are declared via module augmentation in `src/types/next-auth.d.ts`, not inline in `auth.ts`.

**Spotify API access:** the browser never talks to `api.spotify.com` directly (except for unauthenticated `preview_url` MP3s, which need no token). Every other Spotify call is proxied through a Next.js Route Handler in `app/api/spotify/`, using `spotifyFetch<T>()` from `src/lib/spotifyApi.ts` (generic — each call site passes the Spotify response type it expects, from `src/types/spotify.ts`). Non-2xx responses become a `SpotifyApiError` carrying `status`/`path`/`rawBody` (the body is read as text first, so an HTML block page or empty body is still visible in the error instead of silently becoming `null`); routes translate that status into a user-facing message — 429 "rate-limiting", 403 "requires Premium", 404 "no active device". The routes:
- `app/api/spotify/discover/route.ts` (`POST`) — fetches currently-playing (`/me/player`), then the current artist (`/artists/{id}` for genres) and their top tracks (`/artists/{id}/top-tracks`) in parallel, then best-effort genre-filtered Search calls (`/search?q=genre:"..."`) for additional song/artist recommendations. Returns `{ noActivePlayback: true }` if nothing is playing. **Deliberately does not call `/recommendations`, `/related-artists`, or `/audio-features`** — Spotify deprecated all three on 2024-11-27 for any app not already in Extended Quota Mode before that date, and there is no application path to get them back (the reasoning is restated in the header comment of `discover/route.ts`). `currSong` additionally carries genres/release date/duration, built from still-available catalog metadata, not Spotify's own audio-feature ML output. Its response shapes (`DiscoverSuccess`/`DiscoverNoActivePlayback`/`DiscoverError`, unioned as `DiscoverResponse`) live in `src/types/spotify.ts` and are reused as the Redux `updateDiscoverResults` payload type.
- `app/api/spotify/current-track/route.ts` (`GET`) — read-only "what's playing right now", called by `NowPlayingCard` on mount. Fetches `/me/player`, then the current artist (`/artists/{id}`, best-effort — a failed fetch degrades to `genres: []` rather than failing the whole request, since this route runs unconditionally on every mount rather than only on a user-initiated Discover click) and reshapes `item` into the same `CurrSong` DTO discover returns (`songId`/`songUri`/`songName`/`songArtist`/`songArtistId`/`songPicture`/`durationMs`/`releaseDate`/`genres`). It **discards `progress_ms` and `is_playing`**, which is why the transport row and scrubber are dummies (see Component tree) — wiring real playback state starts by widening this response. Returns `{ noActivePlayback: true }` when nothing is playing; for a non-`track` `currently_playing_type` (podcast/ad) it returns `{ error }` **with HTTP 200**, so callers must check `"error" in data`, not just `response.ok`.
- `app/api/spotify/artists/[artistId]/route.ts` (`GET`) — artist page data: `/artists/{id}` and `/artists/{id}/top-tracks?market=US` in parallel, returned as `{ artist, topTracks }` (`ArtistDetailResponse`). Both endpoints survived the 2024-11-27 deprecation; `/related-artists` did not, which is why this page shows top tracks and not similar artists. Fetched client-side by `ArtistDetail`.
- `app/api/spotify/playback/route.ts` (`PUT`) — starts full playback on the user's active device (Premium-only; 403s are translated into a friendly error).
- `app/api/spotify/playlists/route.ts` (`GET`/`POST`) — lists the user's own playlists (owner-filtered), or creates a new playlist and optionally adds a track to it in the same request.
- `app/api/spotify/playlists/[playlistId]/tracks/route.ts` (`POST`) — adds a track to an existing playlist.

All routes run on the Node.js runtime since next-auth's JWT crypto needs Node APIs. Every one of them declares `export const runtime = "nodejs"` explicitly **except** `current-track/route.ts`, which inherits Next 14's Node default instead — don't read that omission as a deliberate edge-runtime choice.

**If you're touching `discover/route.ts`:** don't reach for `/recommendations`, `/related-artists`, or `/audio-features` — they will 403 for this app regardless of scopes or auth state. `SongRow.tsx`/`ArtistCard.tsx` still consume standard Spotify Track/Artist objects either way (Search and Top Tracks return the same object shapes recommendations/related-artists used to), so no component changes are needed if this route's data sourcing changes again.

**Root shell:** `app/layout.tsx` (global styles + providers) → `app/providers.tsx` (client component: `SessionProvider` + Redux `Provider`) → `app/page.tsx` (server component; `getServerSession(authOptions)` decides whether to render `Login` or the signed-in `AppShell` tree — `NowPlayingCard` + `RecommendedSongs` + `ArtistCarousel`).

**Component tree:** `src/components/` is grouped by feature — `shell/` (`AppShell`, `Header`, `GlassBackdrop`), `player/` (`NowPlayingCard`, `AlbumArt`, `TrackMeta`, `DiscoverButton`, `TransportControls`, `TrackProgress`), `songs/` (`RecommendedSongs`, `SongRow`, `EqBars`), `artists/` (`ArtistCarousel`, `ArtistCard`, `ArtistDetail`), `playlists/` (`AddToPlaylistModal`), and `ui/` (`GlassPanel`, `IconButton`, `PillButton`, `StatusPill`); `Login.tsx` sits at the root of `src/components/` since it is the signed-out shell rather than part of any feature. `AppShell` takes `children` and is a **server component**, shared by `app/page.tsx` and `app/artist/[artistId]/page.tsx` — both apply the same `getServerSession` gate. `NowPlayingCard` fetches `/api/spotify/current-track` once on mount (so the card shows the real track — including genres/release date/duration — before the user presses anything), and its "Discover new songs" button calls `/api/spotify/discover` once and dispatches the combined result. **`TransportControls` and `TrackProgress` are deliberately dummies** — play/pause flips a local `useState` icon, prev/next are no-ops, the scrubber moves local state only; nothing there touches Redux or Spotify. They exist because the design calls for them while the state that would drive them (`is_playing`/`progress_ms`) is thrown away by `current-track/route.ts`. `TrackProgress` also falls back to `PLACEHOLDER_DURATION_MS` (210 000 ms — 3:30) whenever `currSong` is `null`, i.e. before the mount-time fetch resolves or when nothing's playing, so the bar never renders as an empty 0:00 track. Every m:ss string (`SongRow`, `TrackMeta`, `TrackProgress`) goes through `formatDuration(ms)` in `src/lib/format.ts` — extend that rather than re-rolling the arithmetic. `SongRow` owns a 30-second `preview_url` snippet player; only one can play at a time, coordinated via `nowPlayingTrackId` in `songSlice` — each row pauses itself in a `useEffect` when Redux says a different track became active. **Keep `isPlaying` derived (`nowPlayingTrackId === track.id`), never mirrored into local state**, and keep the pause in the effect rather than the click handler: the *other* rows never run the handler. Each row also cleans up its audio on unmount, which matters because `updateDiscoverResults` replaces the whole recommendations array while a clip may still be playing. `AddToPlaylistModal` lazy-fetches the user's playlists when it opens (not on page load). `ArtistCarousel` renders only the first 5 (`VISIBLE_SLIDES`) of the up-to-9 artists discover returns, so widening the carousel needs no API change.

**State management:** Redux Toolkit, `src/store/store.ts` (exports `RootState`/`AppDispatch`), one slice (`src/store/songSlice.ts`) for currently-playing/song+artist recommendations/`noActivePlayback`/now-playing-track. Components use the typed `useAppDispatch`/`useAppSelector` hooks from `src/store/hooks.ts` rather than raw `react-redux` hooks, so selector/dispatch calls are inferred instead of implicit-`any`. There is no user/auth slice — identity comes from next-auth's `useSession()` directly (see `src/components/shell/Header.tsx`), to avoid a second, driftable source of truth for something the session cookie already owns.

**Styling:** Tailwind CSS v4 (CSS-first — there is no `tailwind.config.js`; tokens live in the `@theme` block of `app/globals.css`, wired through `postcss.config.mjs`). `app/globals.css` is the **only** stylesheet in the repo — the eleven co-located per-component CSS files are gone, as are Bootstrap, Material-UI v4, and `react-owl-carousel`/jQuery. Headless interactive primitives (menu, modal, buttons, text fields) come from `react-aria-components`, with the `tailwindcss-react-aria-components` plugin providing state variants (`hover:`, `pressed:`, `selected:`) — note the plugin maps `['hover', 'hovered']` (first element is the Tailwind variant name, second is the data attribute), so it's `hover:` targeting `[data-hovered]`, not `hovered:`; likewise `focus:` not `focused:`, and `read-only:` not `readonly:`. Unknown variants are silently dropped by Tailwind, so a typo here never fails a build — it just emits no CSS. Fonts are self-hosted via `next/font/google` (Inter for body, Space Grotesk for display) exposed as `--font-inter` / `--font-space-grotesk`. Shared multi-property recipes are `@utility` rules: `glass-panel`, `glass-header`, `glass-menu` (the account dropdown's popover), `accent-gloss` — `glass-header` is currently referenced by nothing, so like an unused `@theme` token it emits no CSS at all. What utilities can't express lives as plain CSS at the bottom of `globals.css`: the `[data-layer="gradient"]` / `[data-layer="blobs"]` rules painting `GlassBackdrop`'s fixed wash and its three colour blobs (one `filter: blur(90px)` on the group, so there are no per-blob edge seams), plus `@keyframes` — `menu-in`/`menu-out` for the `Header.tsx` account dropdown, driven off react-aria's `entering:`/`exiting:` variants (RAC holds the unmount until the exit animation finishes), and `sr-bar` for `EqBars`. **Note:** Tailwind v4 tree-shakes unused `@theme` tokens, so a token you just added won't appear in the built CSS until something references it. No `@media` queries in the stylesheet yet — a responsive pass is still outstanding; the only motion-preference check anywhere is JS-side, in `ArtistCarousel`'s autoplay effect.

**TypeScript:** `strict: true`, `allowJs: false` — the whole app is TS/TSX, no mixed JS. `src/types/spotify.ts` holds real (importable) interfaces for the Spotify Web API objects this app actually uses (Track, Artist, Album, Playlist, paging, etc.) plus the app's own bespoke DTOs (`CurrSong`, `DiscoverResponse`) — the latter are deliberately distinct types from the raw Spotify shapes since the discover route reshapes data before sending it to the client. `src/types/` also holds ambient declarations: `next-auth.d.ts` (Session/JWT module augmentation), `css.d.ts` (`*.css` side-effect imports, still needed for `app/globals.css`), and `svg.d.ts` (`*.svg` imports as `string`). The app's response unions (`DiscoverResponse`, `CurrentTrackResponse`, `ArtistDetailResponse`) are discriminated **by key presence**, not by a tag field, and every consumer narrows with `"error" in data` / `"noActivePlayback" in data` — new response types must follow that pattern (disjoint required keys, no shared optional fields) or narrowing silently breaks under `strict`. `src/lib/errors.ts` exports `getErrorMessage(error: unknown)`, used everywhere a `catch` block needs `.message` off an unknown error.

**Scaling note:** stateless JWT sessions + no DB scale horizontally on Vercel by construction. The actual ceiling at scale is Spotify's own platform, not the app: apps default to a 25-user cap ("Development Mode") until submitted for Extended Quota Mode in the Spotify Developer Dashboard.
